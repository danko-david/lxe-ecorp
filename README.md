# ECorp - Samba AD and GitLab-based Corporate Infrastructure Lab

A reference architecture showcasing a GitLab-based corporate infrastructure for development-oriented companies. This project is a conceptual model designed to:

1. Demonstrate the structural components of a modern developer environment, including AD/DC and integrated CI/CD.
2. Provide a modular foundation for experimenting with personal projects in a controlled setting.
3. Offer a sandbox for building and testing automated deployment workflows.

The project is organized into submodules covering core services, corporate add-ons, and example application environments to serve as a starting point for infrastructure experimentation.

_Important note_: This installer makes unusual modifications on the host system: it deactivates docker network isolation and modifies routes, so it is better to deploy it in an LXC container or in the provided wrap container (see [Ways to run](#ways-to-run)).

_This is a lab, not a hardened setup_: default passwords are public, the management web interface is open unless you set a password for it and can start provisioning, and several containers hold the docker socket. Do not expose it to a network you do not trust.

## Core infrastructure

The infrastructure is wrapped around 3 core technologies:

- samba _for_ Active Directory Domain Controller functionalities
- gitlab _for_ code management and CI/CD
- dns _for_ dns server to serve custom DNS records and delegated zones

They run as one docker compose project (`ecorp`) on one bridge network:

| Service | What it does |
| --- | --- |
| [`dns`](doc/dns.md) | CoreDNS. Serves the zone of all containers (`ECORP_DNS_CORE_ZONE_NAME`) and forwards delegated names to project servers. Its configuration is generated by the controller into `data/dns/`. |
| [`dc`](doc/dc.md) | Samba AD domain controller (`units/dc`). Also the DNS server every container uses; it forwards to `dns`. |
| [`controller`](doc/controller.md) | Provisions the others with Ansible (`units/controller`), regenerates the DNS zone whenever a container starts or stops, and serves the management web interface. |
| [`host-controller`](doc/host-controller.md) | Runs in the network namespace of the host (`units/host-controller`): opens docker's network isolation and keeps host routes in sync with the `network_route` label of containers. Takes both back when it is stopped. |
| [`gitlab`](doc/gitlab.md) | GitLab CE, connected to the domain controller through LDAP. |
| [`core-gitlab-runner`](doc/gitlab.md) | GitLab runner, registered automatically as two instance runners: one tagged `core` with access to the docker socket and one shared runner for untagged jobs. |

Every container is reachable as `<compose service>.<ECORP_DNS_CORE_ZONE_NAME>`, with the defaults for example `http://gitlab.e-corp.intra.net` and `http://controller.e-corp.intra.net` (management web interface). Nothing is published on host ports: the machine you browse from needs a route to `NET_CIDR` and `NET_DC` as its DNS server.

Containers started by other projects on this docker host can take part through labels:

| Label | Effect |
| --- | --- |
| `dns_names` | Extra DNS names for the container, space separated. |
| `dns_mode=delegated` | The container runs its own DNS server: requests for its names are forwarded to it. |
| `network_route` | A network (CIDR) behind the container; the host gets a route to it through the container. |

## Usage

Requirements: Linux, docker with the compose plugin, bash. Everything goes through the helper script, `./ecorp` without arguments lists the commands.

```bash
./ecorp up        # prepare, build, start, then follow the provisioning until it ends
```

| Command | What it does |
| --- | --- |
| `prepare` | Spawns `.env`, `settings/ad-users.yml` and `settings/steps.yml` from their `.default` files if they do not exist yet, and creates the data directories. |
| `up` | `prepare`, starts the stack and follows the provisioning. |
| `provision` | Runs the provisioning again, for example after editing a file in `settings/`. |
| `follow_provision` | Follows the output of the running provisioning. |
| `purge` | Stops the stack, removes its volumes and everything under `./data`. `.env` and `settings/*.yml` are kept. The firewall rules and routes added on the host are removed as the host-controller stops. |
| `run_in_container` | Starts the whole stack inside the wrap container instead of directly on the host. |
| `build_diorama_image` | Builds `ecorp-diorama`: an image that contains the installed and provisioned stack. |
| `run_tests` | Runs the offline tests. |
| `run_tests_install` | Runs the tests that check a running, provisioned stack. |
| `ci_test_infra`, `ci_ensure_diorama`, `ci_weekly_diorama` | What the CI pipeline calls, see [CI/CD](#cicd). |

Provisioning is an Ansible playbook run inside the controller, at every start of the controller and on request. It sets the GitLab URL, creates the root access token, publishes all `ECORP_*` variables as GitLab instance CI/CD variables, imports roles and users into the domain controller, connects GitLab to it, registers the runners and finally executes the steps. Logs are kept in `data/controller/provision/logs/` and can be followed in the web interface too. `./ecorp provision` and `./ecorp up` exit with the status of the provisioning.

## Ways to run

- **On the host**: `./ecorp up`. Changes the firewall and routes of the host, see the note above.
- **In the wrap container**: `./ecorp run_in_container` starts a systemd + docker container (`dev/wrap_container`), clones the committed state of this repository into it and runs `./ecorp up` there. At the end it prints the route to add on the host.
- **Diorama image**: the stack baked into one image, trading image size for start time. Either `./ecorp build_diorama_image` or the published `lxeu/ecorp-diorama` ([Docker Hub](https://hub.docker.com/r/lxeu/ecorp-diorama)).

Details, the compose file to start the diorama and the published tags: [doc/diorama.md](doc/diorama.md).

## Configuration

### `.env`

Spawned from `.env.default` by `prepare`. The default file is evaluated by bash at that moment, so `$( )` in it is resolved once and `\$` is kept as a reference. Edit `.env` before the first `up`; most values are baked into the domain and GitLab at first provisioning.

| Variable | Default | Meaning |
| --- | --- | --- |
| `NET_CIDR` | `192.168.69.0/24` | Subnet of the docker bridge all infrastructure containers are attached to. |
| `NET_DC` | `192.168.69.10` | Static address of the domain controller, which is also the DNS server of the containers. |
| `NET_DNS` | `192.168.69.9` | Static address of CoreDNS, the forwarder of the domain controller. |
| `DC_REALM` | `ecorp` | Realm of the domain; also the LDAP base (`DC=ecorp`). |
| `DC_DOMAIN` | `ecorp.intra` | Domain (workgroup) of the domain controller. |
| `DC_ADMIN_PASS` | `Passw0rd` | Password of the domain `Administrator`. |
| `GITLAB_ROOT_PASSWORD` | `@Password123` | Password of the GitLab `root` user. |
| `HOME_WWW_USER`, `HOME_WWW_PASSWORD` | not set | Set both to protect the management web interface with a user name and password. |
| `ECORP_DNS_SERVER_IP` | `$NET_DC` | DNS server for resolving internal names, for use by pipelines. |
| `ECORP_CORE_NETWORK_BRIDGE` | `ecorp_core` | Name of the docker network of the stack, for projects that deploy containers into it. It has to stay the name compose gives the network. |
| `ECORP_DNS_CORE_ZONE_NAME` | `e-corp.intra.net` | DNS zone of the containers on this host. |
| `ECORP_HOST_STORAGE_ROOT` | `<project>/data/storage` | Where project servers keep their storage on the host. |
| `ECORP_SSH_EXTRA_AUTH` | empty | Extra SSH public keys, one per line, accepted by the controller and by every machine managed by this system, next to the key the controller generates for itself. See [doc/controller.md](doc/controller.md). |

All `ECORP_*` variables are also set as instance level CI/CD variables in GitLab, so every pipeline sees them; `ECORP_SSH_EXTRA_AUTH` arrives there with the key of the controller in front. The other ones are only used by this stack.

### `settings/ad-users.yml`

Users of the domain with their roles; every role becomes a group. Imported again when the file changes and provisioning runs. A user needs `user`, `password`, `given_name`, `surname` and `roles`; `title`, `email` and `initial` are optional.

### `settings/steps.yml`

Steps executed at the end of provisioning, in order, once per content of the file: they run again when the file changes. A step is a role in `units/controller/code/ansible/roles/step/`, so adding a directory there adds a step type.

| Step | Parameters | What it does |
| --- | --- | --- |
| `git_repo_set_import` | `repos`: list of `url`, `path`, `repo` | Mirrors each git repository into GitLab as the public project `path/repo`. |
| `wait_pipelines` | `pipeline.project` | Waits until the pipelines of a project are finished; fails if the latest one failed. |
| `run_job` | `job.project`, `job.ref`, `job.job`, `job.vars` | Starts a pipeline on a project, runs the named job of it and waits for the job. |
| `create_project_server` | `project_server`: `name`, `type`, optionally `network_route`, `network_size`, `dns_mode`, `discovery_port`, `creator`, `link.project`, `link.tags` | Creates a project server through the `custom-create` job of the project-server module, optionally with a runner bound to a project. |

`steps/` holds ready-made step files to copy into `settings/steps.yml`, for example `steps/lxe-base-repos.yml` which also imports and builds the build images.

## CI/CD

`.gitlab-ci.yml` only calls the helper script:

- `offline-tests` runs `./ecorp run_tests` on every pipeline.
- `build-diorama` (on `master`) runs `./ecorp ci_ensure_diorama`: builds and publishes `ecorp-diorama:<ECORP_VERSION>` and `latest` unless that version is already in the registry. Raising the version in `./ecorp` is therefore what publishes a new image.
- `weekly-diorama` (scheduled pipelines on `master`) runs `./ecorp ci_weekly_diorama`: rebuilds the current version on the newest base images and publishes it as `<ECORP_VERSION>-w<week>` and `latest`. It needs a pipeline schedule in GitLab.
- `autotest-default-install` (manual, or automatic with `PIPE_AUTOTEST`) runs `./ecorp ci_test_infra`: a full install in a container, followed by the install tests. The job fails if the install or a test fails.

Variables these read:

| Variable | Meaning |
| --- | --- |
| `REPO` | Prefix of the published image name, with trailing slash: `lxeu/` on Docker Hub, `registry.example.com/group/` on another registry. Without it nothing is pushed. |
| `DOCKER_REGISTRY_USERNAME`, `DOCKER_REGISTRY_PASSWORD` | If the user name is set, log in to the registry with these before pulling and pushing. |
| `DOCKER_REGISTRY` | Registry to log in to; empty means Docker Hub. If `REPO` is not set, the prefix is `<DOCKER_REGISTRY>/`. |
| `FORCE_BUILD_IMAGE` | Build the diorama image even if the version already exists. |
| `NOT_LATEST` | Do not move the `latest` tag to the built image. |
| `PIPE_AUTOTEST` | Run the install test automatically instead of manually. |
| `CATCH_CONTROL` | Makes a job wait forever before its work, to enter the job container for debugging. |

## Tests

- `./ecorp run_tests` runs every executable in `tests/offline/`. They need no docker and no network and check the helper script, the spawning of configuration, the consistency of the compose file, the playbook and the step files, and what the CI commands do with docker (against `tests/fake/docker`, which only records its calls). An argument selects tests by a part of their name.
- `./ecorp run_tests_install` runs `tests/install/` against a running, provisioned stack on the machine where it runs: the access token, the SSH keys, the web interface, the firewall rules of the host-controller, the imported users, and a second provisioning. They restart the host-controller.
- `./ecorp ci_test_infra` is the full test: installs the stack from zero in a container and runs the install tests in it. Needs docker and the internet, and takes a while.

## Directories

| Path | Content |
| --- | --- |
| `ecorp` | The helper script, the entry point for everything. |
| `units/` | One directory per self-built service: `dc`, `controller`, `host-controller`, each with its `Dockerfile` and its own helper script. |
| `units/controller/code/ansible/` | The provisioning playbook and its roles. |
| `units/controller/code/www/` | The management web interface (bash CGI). |
| `settings/` | Configuration you edit, spawned from `*.default`. |
| `steps/` | Ready-made step files. |
| `doc/` | Documentation of the units, also shown in the management web interface. |
| `dev/` | The wrap container, the diorama image and the CI install test. |
| `tests/` | Offline tests, install tests and the fake docker they use. |
| `data/` | Runtime state of every service, ignored by git, removed by `purge`. |
